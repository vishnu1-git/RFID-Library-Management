Executive Summary

Modern campus library modernization projects encounter a catastrophic recurring pitfall: third-party automation tools and RFID retrofits execute raw SQL modifications against legacy Integrated Library Management Systems (ILMS), permanently corrupting bibliographic catalogs and cascade circulation trees.

LibraSync is engineered to eliminate this failure mode entirely. Designed as an enterprise-grade Modular Monolith, LibraSync maintains its own operational database (PostgreSQL 16 with zero-friction development fallback to SQLite) and communicates with legacy ILMS platforms strictly through standardized, read-only protocol boundaries (NCIP 2.0 and 3M SIP2).

The system delivers a modern React 19 staff portal, a device-neutral Python RFID middleware layer supporting UHF EPC Gen 2 tags and 13.56 MHz contactless smart cards, an offline-resilient security gate with optical CCTV incident capture, and a 4-stage Excel migration pipeline featuring duplicate detection and atomic rollback.

Architectural Rationale: Why a Modular Monolith?

The evaluation criteria require clean boundaries without unnecessary operational fragility. Microservices introduce distributed transactions (2-Phase Commit / Sagas), network serialization latency, and inter-service failure modes that add risk to a single-site library deployment. LibraSync organizes domain services in-process with strict dependency injection. If physical site distribution later requires isolating the RFID listener, the rfid-middleware/ module can be decoupled into an independent network daemon with zero modifications to application domain services.

3. External ILMS Protection & Protocol Isolation Boundaries

The Cardinal Rule (AISYS SOP Pages 1 & 3)

"The solution must not modify, delete, or corrupt existing library records. Under no circumstances should the system alter the existing database."

LibraSync strictly guarantees legacy ILMS preservation through four architectural guardrails:

  1. Dedicated Operational Storage: LibraSync operates exclusively on its own dedicated database (librasync). No database connection string, ORM model, or query in LibraSync has write access to external ILMS databases (such as Koha, Sierra, or Voyager).
  2. Standard Protocol Boundaries: Inter-system synchronization is mediated via standard protocol messages:
    • NCIP 2.0 (NISO Z39.83): Standardized ItemCheckedOut, ItemCheckedIn, and LookupUser XML/JSON payloads.
    • 3M SIP2: Item Information (17), Checkout (11), Checkin (09), and Patron Status (63) messages.
  3. Read-Only Adapters: External catalog queries read through backend/app/integrations/ilms/base.py. If the legacy endpoint is offline, LibraSync serves requests seamlessly from its local operational cache.
  4. Immutable Audit Logging: Every circulation action, migration batch, and staff transaction writes to an append-only audit_logs table.

5. Circulation Lifecycle & EAS Security Bit State Machine

The Electronic Article Surveillance (EAS) security bit controls physical loss prevention across library exit perimeters:

Lifecycle State EAS Security Bit Item Status Perimeter Gate Action Automated Business Logic
In Stacks ARMED (True) AVAILABLE TRIGGER ALARM + CCTV Item resting on library shelf. Any egress triggers the 3D gate siren and logs an unauthorized removal incident.
Checked Out DISARMED (False) ISSUED PERMIT PASSAGE Staff desk validates patron active state, checks loan limit (max 4 books), and disarms the RFID tag bit upon successful issue.
Returned RE-ARMED (True) AVAILABLE TRIGGER ALARM + CCTV Staff check-in pad scans item, calculates overdue fines ($2.00/day overdue), re-arms tag bit, and restores item to catalog.

Borrowing Restriction Rules (AC 04)

  • Reference-Only Volumes: Items linked to bibliographic records with is_reference_only = True are strictly non-circulating. Any check-out attempt is rejected immediately with an HTTP 400 validation error.
  • Blocked / Delinquent Patrons: Borrowers flagged with status BLOCKED or carrying overdue fines exceeding $100 are rejected immediately at the circulation desk.

6. Handheld RFID Shelf Auditing & Misplacement Engine (AC 05)

Stock verification leverages the handheld mobile wand to interrogate shelf tags in bulk. As tags are read, the system cross-references each physical copy against its registered shelf location: 

def evaluate_shelf_collision(scanned_epc: str, target_shelf: str) -> InventoryRead:
    item = db.query(BookItem).join(RFIDTag).filter(RFIDTag.epc == scanned_epc).first()
    is_misplaced = (item.shelf_location != target_shelf)
    return InventoryRead(epc=scanned_epc, is_misplaced=is_misplaced, expected=item.shelf_location)

Misplaced items (e.g. an Architecture book resting in Computer Science) trigger an immediate visual amber alert displaying the expected shelf, and missing catalog items are identified upon session finalization.

7. Perimeter Loss Prevention & Offline Gate Autonomy (AC 06 & AC 09)

When an unissued book passes through portal GATE-PORTAL-01:

  1. The 3D gate antenna detects security_bit == True.
  2. Perimeter alarm sirens sound and visual flashing warning strobes activate.
  3. Integrated optical CCTV camera adapter captures an evidentiary timestamped snapshot frame.
  4. An incident record is written to gate_events and security email alerts are dispatched.
Offline Gate Resilience Architecture (AC 09)

If campus network connectivity to the server fails, the SecurityGateReader switches to Offline Autonomous Mode. The gate evaluates tags against an in-memory offline_security_cache, triggers local alarm sirens autonomously, and appends events to a persistent offline_event_queue that automatically synchronizes with the server once connectivity is restored.

8. Staging-First Spreadsheet Migration & Atomic Rollback (AC 01 & AC 10)

Importing 20,000+ records directly into production tables causes index corruption and duplicate key collisions. LibraSync implements a strict 4-stage migration architecture:

Stage Pipeline Step Target Storage Safety & Integrity Enforcement
Stage 1 Upload & Staging migration_staging Raw rows are parsed from Excel/CSV and stored in an isolated staging table without touching operational catalog tables.
Stage 2 Validation & Collision Detection migration_errors Scans for format defects, intra-batch duplicate ISBNs, and active operational DB collisions. Conflicts are quarantined with row indices.
Stage 3 Atomic Commit books, book_items Clean staged records are inserted into operational tables inside a single ACID transaction.
Stage 4 Disaster Rollback Operational Tables If an administrative error occurs, rollback_job() purges all operational records created by that batch ID while preserving audit logs.
